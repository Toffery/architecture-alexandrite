# Задание 2. Выбор и настройка мониторинга в системе

## 1. Мотивация

Сейчас сайт подключен к Яндекс Метрике, но после открытия партнерского API этих данных недостаточно. Нужно видеть работу обоих каналов заказов, обмен между CRM и MES и состояние инфраструктуры.

Клиенты жалуются на задержки заказов, а операторы - на медленную работу MES. При этом производственные мощности позволяют выполнять больше заказов. Мониторинг поможет определить, на каких этапах возникают задержки и какие компоненты не справляются с нагрузкой.

Для компании это даст следующие возможности:

- Замечать рост очередей, ошибки и зависшие заказы до обращения клиентов
- Быстрее находить причину проблемы и сокращать время простоя
- Проверять, помогли ли оптимизация запросов, кеширование и выделение расчетных обработчиков
- Планировать увеличение ресурсов по измерениям и не тратить бюджет на лишние серверы
- Следить за долей заказов, выполненных в обещанные три недели

## 2. Выбор подхода к мониторингу

| Часть системы                                    | Подход                                          | Что будем измерять                                                                           | Почему выбран этот подход                                                             |
| ------------------------------------------------ | ----------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Shop API, CRM API и MES API                      | **RED**                                         | RPS, долю ошибок, длительность запросов по операциям                                         | Показывает нагрузку на приложение и качество его работы для пользователей и партнеров |
| Обработчики сообщений и расчетов MES             | **RED**                                         | Количество обработок, ошибки, время выполнения                                               | Позволяет оценивать фоновые операции, для которых успешного HTTP-ответа недостаточно  |
| Серверы приложений, PostgreSQL и сервер RabbitMQ | **USE**                                         | CPU, память, диск, ожидание ресурсов, ошибки                                                 | Помогает понять, какой ресурс ограничивает работу системы и нужно ли масштабирование  |
| Очереди RabbitMQ                                 | **USE** с дополнительными показателями доставки | Размер очереди, сообщения в обработке, скорость поступления и подтверждения, ошибки доставки | Важно видеть накопление работы и ситуации, когда потребители перестали справляться    |
| Прохождение заказа                               | Бизнес-метрики                                  | Количество заказов в статусах, время ожидания, просрочки                                     | Технически исправные сервисы еще не означают, что заказ выполнен вовремя              |

## 3. Метрики и ярлыки

Для технических метрик используем общие ярлыки `environment` и `service`, а для метрик конкретного экземпляра - `instance`. Дополнительные ярлыки указаны в таблицах.

В ярлыки не добавляем идентификаторы заказов и пользователей, имена файлов и полный URL с параметрами, иначе количество отдельных рядов метрик будет постоянно расти. Для поиска конкретного заказа будут использоваться логи и трейсы. Маршрут API записываем как шаблон, например, `/orders/{id}`.

### 3.1. API и приложения

Метрики собираем для всех трех API. Для MES отдельно выделяем получение списка заказов, назначение оператора и запросы расчета стоимости.

| Метрика                                               | Зачем нужна                                                                                                                                     | Дополнительные ярлыки                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| Количество запросов и RPS                             | Показывает рост нагрузки и распределение запросов между операциями. RPS рассчитываем по изменению счетчика запросов                             | `route`, `method`, `channel`                |
| Количество ответов по HTTP-кодам и доля ошибок        | Позволяет увидеть сбои сервера, ограничения запросов и ошибки клиентов. Считаем все коды, а не только 200 и 500. 4xx и 5xx анализируем отдельно | `route`, `method`, `status_code`, `channel` |
| Время ответа API: p50, p95 и p99                      | Показывает типичную задержку и медленные запросы                                                                                                | `route`, `method`, `channel`                |
| Число запросов, которые обрабатываются прямо сейчас   | Помогает обнаружить накопление долгих запросов, даже если RPS не растет                                                                         | `route`                                     |
| Доступность API и успешность контрольного запроса     | Позволяет обнаружить недоступность сервиса, когда ошибок в метриках самого приложения уже нет, потому что оно не отвечает                       | `target`, `check`                           |
| Использование памяти процесса и паузы сборщика мусора | Помогает объяснить задержки, связанные с работой Java и .NET, а не с запросами к БД                                                             | `runtime`                                   |

`channel` имеет ограниченный набор значений: `shop`, `partner`, `internal`, `unknown`. Канал определяем на стороне приложения по точке входа и сохраняем в данных заказа. Запросы партнеров не должны смешиваться с работой операторов MES. Время ответа собираем в гистограммы. Границы для обычных запросов и длительных расчетов задаем отдельно, потому что операции на секунды и расчеты до 30 минут нельзя оценивать по одному порогу. Не усредняем p95 разных экземпляров, будем рассчитывать общий показатель по их гистограммам.

### 3.2. RabbitMQ и расчет стоимости

| Метрика                                                                           | Зачем нужна                                                                                                 | Дополнительные ярлыки                     |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Число сообщений, ожидающих доставки (ready)                                       | Рост показывает, что обработчики не успевают или отсутствуют                                                | `vhost`, `queue`                          |
| Число доставленных, но не подтвержденных сообщений (unacknowledged или in flight) | Показывает объем работы у потребителей. Длительный рост может указывать на медленную или зависшую обработку | `vhost`, `queue`                          |
| Скорость публикации, доставки и подтверждения сообщений                           | Позволяет сравнить поступление работы с ее выполнением                                                      | `vhost`, `queue`, `operation`             |
| Число активных потребителей                                                       | Нужна для обнаружения очереди, которую некому обрабатывать                                                  | `vhost`, `queue`                          |
| Число сообщений в dead-letter очередях и скорость их поступления                  | Показывает сообщения, которые требуют разбора после ошибок, истечения срока или других причин отклонения    | `vhost`, `queue`                          |
| Число повторных доставок, неудачных публикаций и ошибок обработки                 | Помогает обнаружить нестабильность обмена и повторяющиеся сбои                                              | `queue`, `operation`, `error_type`        |
| Время ожидания сообщения до начала обработки и время самой обработки              | Позволяет отделить ожидание в очереди от медленной работы приложения.                                       | `queue`, `message_type`, `outcome`        |
| Число начатых, завершенных и неудачных расчетов стоимости                         | Показывает, сколько расчетов MES выполняет и сколько заканчивается ошибкой                                  | `channel`, `outcome`, `complexity_bucket` |
| Длительность расчета и число одновременно выполняемых расчетов                    | Помогает оценить загрузку MES и эффект выделения фоновых обработчиков                                       | `channel`, `complexity_bucket`            |

`complexity_bucket` - несколько заранее определенных групп по числу полигонов модели, например, простая, средняя и сложная. Границы необходимо будет определить по реальным моделям. `error_type` также ограничиваем известными категориями, без текста исключения. Низкий размер очереди  нужно сопоставлять с показателями заказов и результатами сверки CRM и MES. Метрику ожидания, измеренную при получении сообщения, дополняем проверкой застрявших заказов: если потребитель остановился, новых измерений времени ожидания не будет.

### 3.3. Серверы, базы данных и хранилище

| Метрика                                                                                | Где собираем и зачем                                                                                          | Дополнительные ярлыки            |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| Использование CPU и ожидание процессорного времени                                     | На серверах приложений, брокера и БД. Помогает выявить нехватку вычислительных ресурсов                       | `host`, `component`              |
| Использование и доступный объем памяти, swap и завершения из-за нехватки памяти        | На серверах приложений, брокера и БД. Показывает давление на память и причины аварийных завершений            | `host`, `component`              |
| Свободное место, задержки дисковых операций и очередь I/O                              | На серверах и дисках БД и RabbitMQ. Нужны для обнаружения нехватки места и медленного хранения                | `host`, `device`                 |
| Количество соединений с БД относительно лимита и ожидание соединения в пуле приложения | Для Shop DB, MES DB и пулов всех трех API. Помогает отличить нехватку соединений от медленного SQL            | `database`, `pool`, `service`    |
| Длительность запросов к БД, блокировки и взаимные блокировки                           | Для Shop DB и MES DB. Помогает найти причину медленного списка MES и влияние общей БД на магазин и CRM        | `database`, `operation`          |
| Размер БД и скорость роста                                                             | Для Shop DB и MES DB. Нужны для планирования диска и оценки роста данных                                      | `database`                       |
| Размер S3-хранилища и число объектов                                                   | Для хранилища 3D-моделей. Помогает планировать расходы и рост объема                                          | `bucket`                         |
| Время и ошибки загрузки и чтения 3D-файлов                                             | На стороне приложений, обращающихся к S3. Недоступность модели может остановить расчет даже при исправной MES | `bucket`, `operation`, `outcome` |
| Состояние сбора метрик и время последнего успешного обновления                         | Для всех источников. Позволяет отличить исправную систему от отсутствующих данных                             | `job`, `instance`                |

`operation` - ограниченное название операции без SQL и параметров. Метрики серверов управляемых БД получаем через средства облака. Метрики SQL и ожидания в пулах дополняем измерениями приложений и доступной статистикой PostgreSQL. На сервер управляемой БД собственный агент не устанавливаем.

### 3.4. Прохождение заказов

| Метрика                                                                    | Зачем нужна                                                                                                                            | Дополнительные ярлыки      |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| Число принятых заказов                                                     | Показывает реальную нагрузку от магазина и партнеров. Черновики и корзины не считаем принятыми заказами                                | `channel`                  |
| Число заказов в каждом статусе                                             | Показывает, на каком этапе копится работа                                                                                              | `channel`, `status`        |
| Время завершенных этапов и возраст самого старого заказа в текущем статусе | Помогает обнаружить задержки, включая заказы, которые еще не перешли на следующий этап                                                 | `channel`, `status`        |
| Число заказов без исполнителя с превышенным сроком ожидания                | Помогает проверить гипотезу, что старые заказы остаются без внимания                                                                   | `channel`                  |
| Число открытых просроченных заказов и доля выполненных в обещанный срок    | Показывает результат для клиента. Отдельный счетчик открытых просрочек покажет, не скрыта ли проблема за успешно завершенными заказами | `channel`                  |
| Число расхождений между состояниями заказов в CRM и MES                    | Помогает обнаружить случаи, когда событие не дошло или не применилось                                                                  | `channel`, `mismatch_type` |

Для каждого статуса фиксируем систему, которая отвечает за его изменение. Расчеты по заказам выполняем периодической задачей по сохраненным данным, а не полным обходом таблиц при каждом запросе Prometheus. Один заказ не должен дважды учитываться из-за наличия записей в CRM и MES. Для партнерских заказов используем общий идентификатор и согласованную точку приема заказа в MES.

Начало отсчета обещанных трех недель и конечный этап необходимо согласовать с бизнесом. Долю выполненных вовремя заказов считаем среди завершенных заказов за выбранный период. Порог ожидания в каждом статусе определяем отдельно, поскольку расчет цены и производство занимают разное время. Сверку CRM и MES добавляем вместе с инициативой надежной обработки из Task1. Пока ее нет, показатель расхождений недоступен.

## 4. План действий

1. **Уточнить исходные данные.** Проверить версии приложений, ОС серверов, список очередей, доступные облачные метрики и существующие средства мониторинга. Согласовать точки приема заказа, владельцев статусов и правила расчета просрочки.
2. **Подготовить инфраструктуру мониторинга.** Создать отдельный инстанс, установить Prometheus, Grafana и Alertmanager, настроить сеть, доступы, хранение и контроль доступности мониторинга. Конфигурацию хранить в Git.
3. **Подключить технические метрики.** Для Java-приложений использовать Actuator и Micrometer, для MES - библиотеку метрик .NET, для RabbitMQ - плагин rabbitmq_prometheus, для серверов - системные экспортеры, для управляемых БД и S3 - метрики облака.
4. **Добавить метрики приложений и заказов.** Java-разработчики подключают магазин и CRM, C#-разработчик - MES. Реализовать ограниченный набор ярлыков, гистограммы задержек и периодический расчет состояния заказов. Сверку подключить после ее реализации в рамках Task1.
5. **Собрать дашборды и исходные значения.** В течение первых двух недель сравнивать оба канала, смотреть пики нагрузки и медленные операции. Не ждать окончания этого периода для разбора явных сбоев.
6. **Настроить уведомления.** Согласовать пороги, ответственных и порядок реакции. 
7. **Проверить на release.** Вместе с QA воспроизвести остановку API и потребителя, ошибку обработки сообщения, медленный расчет и потерю доступа к источнику метрик. Убедиться, что графики показывают проблему, уведомления приходят, а отсутствие данных не выглядит как исправная работа.
8. **Внедрить в prod и оценить результат.** Проверить нагрузку от сбора метрик, расход диска и полезность уведомлений. Сравнить задержки, просрочки и время обнаружения сбоев до и после изменений. *При выделении расчетных обработчиков и добавлении кеша расширить мониторинг их показателями.

Основную настройку инфраструктуры выполняет DevOps, метрики в код добавляют разработчики, сценарии проверяет QA. Продакт помогает определить показатели выполнения заказов и правила реакции на просрочки.
